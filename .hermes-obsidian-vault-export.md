# 04 - Lessons Learned

**Project:** From Type 1 to Transcendence  
**Date:** 2026-06-06 (Updated 2026-06-10)

## What Worked Well

- Receiving one strong, detailed prompt first produced better initial results
- Focused add-on prompts worked well for iteration
- Being very specific about behavior (e.g., "hide text while dragging") produced better outcomes
- Referencing "existing website" helped maintain continuity
- Creating a structured Obsidian knowledge base early helped organize thinking
- Maintaining separate focus sessions for different projects (website vs digital products) improved clarity

## What Didn’t Work Well

- Trying to fix too many things in one prompt often led to incomplete implementation
- The AI assistant was not given enough detail early on, resulting in weak performance
- Navigation issues were not addressed early enough
- The Planets section was built as a standalone section instead of being integrated into the UI from the beginning
- Experiments were not emphasized enough in early prompts, leading to basic implementations
- Memory limitations in the AI system (2,200 character cap) reduced long-term continuity across sessions

## Key Improvements for Future Projects

1. Start with a very detailed master prompt that covers all major features
2. Define the AI assistant behavior clearly from the first prompt
3. Address navigation and UX early (smooth scrolling, pop-up behavior, button placement)
4. Decide on integration patterns (e.g., planets in UI) before building
5. Prioritize high-quality experiments in the initial prompt
6. Use numbered, focused add-on prompts for iteration (max 4–5 changes per prompt)
7. Document decisions in Obsidian as they are made
8. When pursuing parallel revenue projects (digital products, YouTube), clearly separate focus sessions to avoid context switching fatigue
9. Memory limitations in AI systems should be proactively managed by maintaining external knowledge bases (Obsidian)

## Recommendations for Grok Composer
## Recommendations for Grok Composer
- Always specify what should be kept vs changed
- Be extremely specific about interaction behavior
- Mention desired user feeling ("polished", "immersive", "not intrusive")
- Include layout preferences early
- Reference existing issues clearly when asking for fixes
- When user is balancing multiple projects (website + digital products + content), confirm primary focus at the start of each session

## Hermes Agent Configuration Lessons (June 2026)

### What Worked Well
- Using `hermes doctor --fix` successfully migrated an outdated config and resolved compatibility issues.
- Running `hermes doctor` first to diagnose problems before making changes.
- Setting `stt.provider = local` and `tts.provider = edge` eliminated XAI-related voice errors.
- Documenting tool limitations (file size caps) allows proactive workflow adjustments (always use offset/limit for large reads).

### What Didn’t Work Well
- Setting XAI as STT/TTS provider caused repeated "empty transcript" errors (XAI is only for the main LLM).
- Not checking config version early led to hidden compatibility problems.
- Attempting to read large files without offset/limit parameters triggered rejections and incomplete data.

### Key Improvements for Future Hermes Use
1. Always verify STT and TTS providers are supported (local or edge recommended for reliability; ElevenLabs for higher quality).
2. Run `hermes doctor` and `hermes doctor --fix` when experiencing unexplained errors.
3. Use credential pools (`hermes auth add`) for managing multiple API keys instead of relying on single keys.
4. For any file or web content > ~80K characters, proactively use `offset` and `limit` parameters.
5. During `hermes setup`, select "local" terminal backend on macOS unless remote/containerized execution is needed.
6. When creating ElevenLabs API keys, enable only the necessary scopes (primarily Text to Speech) to follow least-privilege principles.

### Technical Constraints Discovered
- Tool output size limits are hard constraints: `read_file` (~100K chars), `web_extract` (~2M chars), `browser_snapshot` (~8K chars).
- XAI cannot be used for voice tools.
- Config changes require a session restart (`/reset`) to take effect.

# Hermes Multi-Profile Setup - Background Agent

**Date:** June 2026  
**Status:** Complete  
**Goal:** Set up a second Hermes profile (`background-local`) running a local Qwen3.6 model as a background agent while keeping the main agent in the Hermes Desktop app.

## Summary

We created and configured a dedicated Hermes profile for running a local Qwen3.6 model. This allows running two independent agents simultaneously:

- **Main agent** → Hermes Desktop app (Grok 4.3)
- **Background agent** → Local Qwen3.6 via MLX (running in terminal or Desktop)

## Key Concepts

### Profiles vs Chats

- Each Hermes **profile** is a completely independent agent.
- Each profile has its own model, memory, skills, and configuration.
- You cannot easily swap models inside an active chat — the model is tied to the profile.

### Profiles Created

| Profile Name          | Model                              | Purpose                          | Status |
|-----------------------|------------------------------------|----------------------------------|--------|
| Home (default)        | Grok 4.3 (cloud)                   | Main daily driver                | Active |
| background brain      | Unknown (older profile)            | Previous experiment              | Exists |
| background local      | Qwen3.6-35B-A3B-4bit (local MLX)   | Background / local model agent   | Configured |

## How the Setup Was Done

1. Created new profile:
   ```bash
   hermes profile create background-local
   ```

2. Switched to the profile and ran setup:
   ```bash
   hermes profile use background-local
   background-local setup
   ```

3. During setup:
   - Selected **custom (direct API)**
   - Entered base URL: `http://localhost:8080/v1`
   - Chose **Chat Completions** mode
   - Selected the local Qwen3.6 model
   - Configured tools (cua-driver, Piper TTS, DuckDuckGo, etc.)

## Running the Background Agent

### Option 1: Inside Hermes Desktop App
- Click on **"background local"** in the sidebar to start chatting with the local model.

### Option 2: Terminal (Recommended for Background Use)
Use `tmux` for easy detach/reattach:

```bash
# Start the session
tmux new -s background-local
background-local chat

# Detach (leave running)
# Press: Ctrl + B, then D

# Reattach later
tmux attach -t background-local
```

- Different profiles can (and should) have different models assigned.
- Tools that require API keys (e.g., some web search providers) will be disabled unless configured.

## 04 - AI & Agents/Lessons Learned - Multi-Agent Setup (2026-06-16).md

# Lessons Learned - Multi-Agent Setup (June 16, 2026)

## What Worked

- tmux is effective for running multiple Hermes agents side-by-side in the background.
- The Hermes Desktop app can be used normally while background agents work on the Obsidian vault.
- Background agents can improve note quality over time through organization and research roles.

## What Didn't Work Well

- Repeated changes to the global Hermes config caused conflicts between agents.
- Command-line flags for custom providers were unreliable in Hermes v0.16.0.
- Sessions became "stuck" with incorrect model settings after config changes.
- Starting agents with mixed configs led to repeated 404 errors when trying to use the wrong model with xAI.

## Key Insights

- Global config changes affect all Hermes instances. Separate profiles or explicit per-session configuration is safer.
- When a Hermes session gets into a corrupted state, it is often easier to kill the session and start fresh rather than trying to fix it.
- The most stable way to run different models is to configure them at startup rather than relying on global config.

## Recommendations for Future Attempts

- Use Hermes profiles for different agent types (one profile for Grok, one for local models).
- Avoid mixing config changes across multiple agent sessions.
- Document working command combinations clearly before experimenting further.

## 04 - AI & Agents/Prompt Engineering Patterns.md

# Prompt Engineering Patterns – From Type 1 to Transcendence

**Project:** From Type 1 to Transcendence  
**Date:** 2026-06-06  
**Purpose:** Document effective prompting strategies for Grok Composer and future AI training

## Core Prompting Philosophy

The user strongly prefers:
- Receiving **one strong, detailed prompt** first
- Then iterating with focused add-on prompts
- Clear, structured instructions rather than vague requests

## Effective Prompt Structure Observed

### 1. Initial Master Prompt
- Comprehensive description of the full vision
- Detailed section-by-section breakdown
- Clear design direction and aesthetic
- Specific interactive features listed

### 2. Add-On / Iteration Prompts
- Focused on 3–5 specific improvements at a time
- Always reference "existing website" to avoid full rebuilds
- Clearly state what to add, fix, or improve
- Include both problems and desired behavior

### 3. Common Prompt Elements That Work Well

- Explicitly state what to **keep** vs **change**
- Use numbered lists for multiple changes
- Reference specific sections by name
- Mention desired user feeling ("polished", "immersive", "not intrusive")
- Include technical constraints when known

## Prompting Patterns by Category

### AI Assistant Prompts
- Specify behavior style ("last resort", "helpful but not intrusive")
- Describe hover vs click behavior
- Mention text visibility rules (especially during drag)
- Request contextual help when highlighting text

### Navigation & UX Prompts
- Clearly list buttons or elements to remove
- Specify desired behavior (smooth scroll, close on outside click)
- Mention position of persistent elements (Journey Map)

### Experiment & Interaction Prompts
- Emphasize quality over quantity
- Request "advanced and meaningful" interactions
- Specify stacking or layout preferences
- Reference existing problems ("currently not interactive enough")

### Planet Integration Prompts
- Clearly state removal of dedicated section
- Request planets to be "scattered throughout the UI"
- Specify interaction expectations (click, rotate, show information)

## Lessons Learned

- Too many changes in one prompt can lead to incomplete implementation
- Being very specific about behavior (e.g., "hide text while dragging") produces better results
- Referencing "existing website" helps maintain continuity
- Combining multiple related fixes into one prompt works better than many small prompts

## Recommended Future Prompt Style

When creating new prompts:
1. Start with what to improve
2. List specific problems
3. Describe desired behavior in detail
4. Mention what should remain unchanged
5. Keep the prompt focused (max 5–6 major changes per prompt)
